## 1. なぜ作るのか

介護現場のリーダーが、リーダーシップをもっと発揮していきたいと考えたとき、
**まず自分のリーダータイプを見きわめ、長所を生かして短所を補う**方針を立てられるようにしたい。〔ゆ〕

このアプリの一番の役目は、使う人本人に次の答えを返すこと。

- 自分はどんなタイプのリーダーか
- 何を生かし、何をどう補えばよいか
- 半年でどう成長していくか（具体的なステップ）

## 2. 誰が使い、どう広がるか〔ゆ〕

1. **作った本人（介護リーダー）**（一番の利用者）
2. **職場のスタッフ**：「おもしろいから答えてみて」と誘う範囲。人事や評価とは切り離す
3. **インターネットで一般公開**：おもしろければ、介護職の人なら誰でも使えるように公開する

## 3. 成功の基準・目標・やらないこと

### 3-1. 成功の基準〔ゆ〕

- **当たっている**と感じる
- 読んだあとに**前向きになり、やる気が上がる**

### 3-2. 目標

- 自分のリーダータイプと、長所・のびしろ・補い方がわかる
- のばしたいところを自分で選び、半年分の成長ステップが手に入る
- スマホ・タブレット・パソコンのどれでも読みやすい
- LD・ディスレクシアのある人でも読みやすい

### 3-3. 目標にしないこと（v1）

- スキル・肩書き・相性・チーム機能（あとの版。§13）
- 正式な心理検査としての正確さ
- ログインやアカウント

### 3-4. これをしたら失敗（技術的に動いても）

- 読んだ人が**落ち込む**、または「決めつけられた」と感じる
- 人事評価や査定の道具として使える形になる
- 回答や結果が**外部に送られる**
- 文字が小さい・つまっている・色だけで区別しているなど、読みにくい

## 5. 性格モデルと判定

### 5-1. 軸・動物・グループ・型（作成考慮案 §4 のまま）

- **5本の軸**（A〜E）：関わり方・見るところ・進め方・変化への姿勢・気持ちの安定（ビッグファイブがもと）
- **16の動物**：A〜D の4本の軸の組み合わせで決まる（コード例 `LTFK`）
- **4つのグループ**：A × B で決まる。けん引・まとめ役・職人・寄りそい
- **型**：E 軸。どっしり型／こまやか型
- 表示名：`{動物}・{型}`（例：ライオン・どっしり型）。コード：`LTFK-D`
- 動物16種は作成考慮案の**仮案のまま**進める。イラストを作る前に、一覧で作者に確認する〔C〕

### 5-2. 質問と答え方

- 性格の質問：**40問**（1軸8問）。うち各軸の半分（4問）は**逆向き**（`direction` が反対側）〔C〕
- 答え方：**5段階**（そう思わない／あまりそう思わない／どちらともいえない／ややそう思う／そう思う）〔C〕
  - 今の `questions.json` と同じ。逆向きの質問で、なんとなくの回答をおさえる
- 介護現場の場面を使った質問を多めにする（作成考慮案 §8）
- 質問の出す順番：軸がかたよらないよう、**固定の順番**でまぜて出す（毎回ランダムにはしない）〔C〕
  - 理由：テストしやすく、途中保存から再開しても順番が変わらない

### 5-3. 点数の計算〔C〕

1. 答えを 1〜5 の数にする（「そう思わない」＝1 … 「そう思う」＝5）
2. 質問の `direction` が `right` ならそのまま、`left` なら `6 − 答え` にする（＝右側に寄るほど大きい数）
3. 軸ごとに平均し、`(平均 − 1) ÷ 4 × 100` で **0〜100 の「右側寄り度」** にする
4. 50 未満なら左側、**50 以上なら右側**の文字をコードに使う（`axes.json` の note どおり）
5. 表示は、寄っている側の％にする（例：右側寄り度 28 → 「引っぱる 寄り（72％）」）
6. 右側寄り度が **40〜60**（`axes.json` の `balanceRange`）なら「◎ バランス型（どちらもできる）」と表示する
   - バランス型でも、動物と型の判定には 4. の結果を使う

- 判定はすべて**副作用のない関数**にし、Vitest でテストする
- 答えていない質問がある状態では結果を出さない

### 5-4. 判定のしくみの文書

- 計算の詳細は `docs/03_scoring-logic.md` に書く（計画の中で作る）

## 6. 画面の流れ

1. **トップ**：アプリの説明、注意書き（§10）、「はじめる」／「つづきから」／「前回の結果を見る」
2. **質問**：1画面1問。進み具合のバー（○／40）、戻るボタン。答えるたびに端末に保存
3. **結果**：§7 の構成。「もう一度やる」「結果を消す」ボタン〔C〕

- 「結果を消す」は、端末に保存した回答と結果をすべて消す（プライバシーのため）〔C〕
- 1つの端末に保存する結果は**1人分**（最新の1回）〔C〕
- 「もう一度やる」を押しても、前回の結果は**新しく40問を答え終えるまで残す**。やり直しの途中でやめても、トップから前回の結果を見られる〔ゆ〕

## 7. 結果ページ

たたき台：`.superpowers/brainstorm/486-1792730463/content/result-page-v2.html`（構成）と `color-direction.html`（見た目、案A）。

### 7-1. 構成（上から順に）〔ゆ〕

| 順 | 部分 | 中身 |
|---|---|---|
| 0 | **入口** | イラスト、グループ名、`{動物}・{型}`、キャッチコピー、ひとこと説明。**強みだけ書く（のびしろは出さない）** |
| 1 | **5つのかたむき** | 5本の軸のバー。●の位置＋「〜寄り（○％）」の文字＋軸のアイコン。バランス型の表示 |
| 2 | **長所と、のびしろ** | 5本の軸それぞれのカード（その人が寄っている側の内容） |
| 3 | **リーダーとして** | ★強み／△クセ／◇ヒント |
| 4 | **部下として** | ★強み／◇伝わる指示／♪やる気の出る声かけ |
| 5 | **成長ステップ** | 本人が5本の軸から1つ選ぶ → ①明日から ②1か月 ③3か月 ◎半年後の目標 |

- 「短所」という言葉は画面で使わず、「のびしろ」「気をつけたい」と書く〔C〕

### 7-2. 文章を作る単位〔C〕

| 部分 | 単位 | 数 |
|---|---|---|
| 入口のひとこと | 動物ごと（16）＋型ごとの一文（2） | 18 |
| 長所とのびしろ | 軸の側ごと | 10 |
| リーダーとして・部下として | 動物ごと | 16 |
| 成長ステップ | 軸の側ごと | 10 |

- 成長ステップで選んだ軸が**バランス型**のときは、その人が寄っている側（§5-3 の 4.）のステップを出す〔C〕
- 成長ステップで選んだ軸は端末に保存し、次に開いたときも同じものを出す〔C〕

### 7-3. 文章の書き方ルール〔ゆ〕

`docs/04_writing-guide.md` にまとめる（計画の中で作る）。中心は次のとおり。

- **入口は強みだけ**
- 各軸のカードは **△気をつけたい（短く・一文）→ 〇やってみる → ★あなたの力（長く）→ 強みがのびた先** の順
  - 人は最後に読んだことが心に残るので、**強みで終える**
  - 長さの目安：強み ＞ のびしろ（強みが一番長い）
- のびしろは**強みの裏返し**として書く（「スピードがあるぶん、〜」）
- 「〜かもしれません」で**決めつけない**
- 強みは**介護の具体的な場面**で書き、まわりへの良い影響まで書く
- 補い方は「短所を直す」ではなく「**その強みがもっと活きる方法**」として書く
- 中学生にわかる言葉。1文は50字以内

**お手本（引っぱる側）**

> △ 気をつけたい
> スピードがあるぶん、まわりの声を拾いきれないことがあるかもしれません。
>
> 〇 やってみる
> 決める前に一人だけ「どう思う？」と聞いてみてください。
>
> ★ あなたの力
> それでも、あなたの一番の力は決断の早さです。利用者さんが急に具合を悪くしたとき、まわりが迷っているあいだに「看護師さんを呼んで。ここは私が見ます」と動けるのがあなたです。その力に、チームはきっと何度も助けられています。まわりの声をひとつ足せば、その決める力はもっと信頼される力になります。

**成長ステップのお手本（引っぱる側）**

| 時期 | 内容 |
|---|---|
| ① 明日から | 決める前に一人だけ「どう思う？」と聞く |
| ② 1か月 | 申し送りで、毎回一人に意見を聞く |
| ③ 3か月 | 会議で、まだ話していない人に話をふる |
| ◎ 半年後の目標 | 「決めるのが早くて、話も聞いてくれる人」と言われる |

### 7-4. 文章の下書きと確認

- 全部の文章（§7-2 の合計 54 項目と、質問40問）は Claude が下書きし、**作者が読んで直す**〔C〕
- 文章は `data/` の JSON に入れる。`axes.json` には、強みの長い文章（介護の場面）と成長ステップの欄を足す

### 8-2. イラスト〔ゆ〕

### 8-3. 色〔ゆ〕

- アプリ全体の土台：**案A「コーラル × ミント」**

### 8-4. 読みやすさ（LD・ディスレクシア対応）〔ゆ〕

- **文字は大きめ**：本文 18px（スマホ）／19px（タブレット）／20px（パソコン）。見出し 22px 以上。**15px 未満は使わない**
- 行間 1.85、文字の間 0.04em、左そろえ（両端そろえにしない）、斜体を使わない
- 1行は約34文字まで（`max-width: 34em`）
- △〇★ などのラベルのあとで改行する
- **色だけで区別しない**：記号・枠・太字・バッジをいっしょに使う
- **真っ白・真っ黒を使わない**
- 押すところは高さ・幅 44px 以上
- ダークモード（`prefers-color-scheme: dark`）に対応。動きを減らす設定（`prefers-reduced-motion`）に対応
- **フォント：本文は教科書体**（ディスレクシア対応として）〔ゆ〕。見出し・ボタン・数字は BIZ UDPゴシック〔C〕

| 使う場所 | 指定の順番（左から先に使う） |
|---|---|
| 本文 | ① 端末に入っている「UD デジタル 教科書体」→ ② 同梱の **Klee One** → ③ 同梱の BIZ UDPゴシック |
| 見出し・ボタン・数字 | ① 同梱の BIZ UDPゴシック（太字）→ ② 端末の UD デジタル 教科書体 太字 |

- **UD デジタル 教科書体は同梱しない**〔C〕
  - モリサワの書体で、Windows に入っているものはウェブに載せて配る許可がない
  - ウェブで使う正式な方法はモリサワの有料サービス（TypeSquare）だが、モリサワのサーバーへ通信が発生するので「外部に通信しない」方針に合わない
  - そこで「端末に入っていれば使う」指定にする（Windows のパソコンでは UD デジタル 教科書体で表示される）
- **Klee One（フォントワークス、SIL Open Font License 1.1）を同梱する**〔C〕
  - 鉛筆やペンで書いたような、教科書体に近い形の無料書体。iPhone・Android でも教科書体らしい形で読める
  - 注意：UD デジタル 教科書体のようにディスレクシア向けに研究して作られた書体ではない
  - 太さは Regular（400）だけ。太字は BIZ UDPゴシックの Bold で表す（使わない太さを配らないため）
- BIZ UDPゴシック（モリサワ、SIL Open Font License 1.1）も同梱する
- **どの書体も Google Fonts などから読み込まない**（外部に通信しないため）。`public/fonts/` に置く
- 日本語の書体はファイルが大きい（1書体で数 MB）ので、ビルドのときに**アプリで使う文字だけを取り出して小さくする**（サブセット化。`data/` の JSON と画面の文字から使う文字を集める）
- 同梱する書体のライセンス文（OFL）を `public/fonts/` にいっしょに置く
- 作者の `~/.claude/rules/html-readability.md` のうち、**色の指定だけはこのアプリでは使わない**（ポップにしたいという希望のため）。そのほかの項目は守る〔C〕

### 8-5. 画面の大きさ〔ゆ〕

## 9. イラストの作り方〔ゆ〕〔C〕

1. 動物16種の一覧を作者に確認してもらう
2. 共通の指示文（絵柄Dの条件・制服・名札・背景色・文字なし・真っ白真っ黒なし）を1つ作り、動物名と制服の色だけを入れかえて Codex で作る。お手本画像 `docs/reference/lion-style-d.png` を毎回いっしょに渡し、タッチをそろえる
   - コマンドの例：`codex exec --skip-git-repo-check -s workspace-write -i <お手本画像> -`（指示文は標準入力）
3. できた画像の**背景を透明にする**（Codex の画像は背景が透明にならないため）
4. ウェブ用に小さくする（例：512×512 の WebP / PNG）。ファイル名は `animals.json` の `image` に合わせる
5. あしらい（6〜10個ほど）も同じ手順で作る
6. 作者に一覧で見てもらい、タッチがずれたものだけ作り直す

- 画像の保存先：`public/images/animals/`、`public/images/deco/`
- 試作画像（`.superpowers/` の中）はアプリには使わない

## 11. 作り方（技術）

### 11-1. 構成〔C〕（作者了承ずみ）

| 項目 | 選んだもの |
|---|---|
| 形 | **静的サイト**（サーバーでプログラムを動かさない。PHP は使わない） |

### 11-2. フォルダ構成〔C〕

作成考慮案 §18 をもとに、Vite の決まりに合わせる。

```
kaigo-animal-shindan/
├─ README.md
├─ AGENTS.md / CLAUDE.md     … 作業ルール（同じ内容）
├─ index.html                … Vite の入口
├─ docs/                     … 01〜04 の文書
├─ html/                     … docs の確認用 HTML（Markdown から作る）
├─ data/                     … いまフォルダ直下にある JSON 6つをここへ移す
├─ public/
│  ├─ images/animals/
│  ├─ images/deco/
│  └─ fonts/                 … Klee One・BIZ UDPゴシック（使う文字だけに小さくしたもの）とライセンス文
├─ src/
│  ├─ main.ts
│  ├─ quiz.ts                … 質問の表示と回答
│  ├─ scoring.ts             … 点数計算とタイプ判定（副作用なし）
│  ├─ result.ts              … 結果ページ
│  ├─ storage.ts             … 端末内への保存
│  └─ styles/
└─ tests/
```

- v1 で使わない JSON（`skills.json`・`titles.json`・`compatibility.json`）も `data/` に移して残す
- JSON はビルド時に読みこむ（`import`）。実行中に外から取ってこない
- 保存データには版の番号をつけ、質問が変わったときに古い途中データを安全に捨てられるようにする〔C〕
- 時刻など毎回変わる値は、関数の外から渡せるようにする（テストのため）

### 11-3. 公開のしかた〔ゆ〕

- **リポジトリは公開**にする（無料プランで GitHub Pages を使うため）
- そのため、`docs/` などリポジトリに入れる文書には**個人の事情を書かない**
- 一般公開（アプリ名を決めて広く知らせる）までは、**検索エンジンに載らないようにする**
  - 全ページに `<meta name="robots" content="noindex, nofollow">`、`public/robots.txt` で全体を拒否
  - 一般公開のときに外す
- GitHub Actions でビルドして GitHub Pages に載せる。Vite の `base` はリポジトリ名に合わせる
- リポジトリの作成と公開設定（GitHub 上の操作）は、作者の確認をとってから行う

### 11-4. なぜこの作り方か（第三者への説明用）

確認用 HTML（`html/02_requirements.html`）では、この章を中学生にもわかる説明とたとえ付きで載せる。要点は次のとおり。

- **静的サイト**：パンフレットを置いておくようなもの。受付の人（サーバー）がいないので、攻撃される場所がほとんどない。無料で速い。回答を外に送らないと言い切れる。比べた相手：PHP / WordPress（受付が狙われる・更新とお金が必要）、スマホアプリ（審査・2種類作る必要）、診断メーカーやフォーム（見た目や判定を自由に作れない）
- **GitHub Pages**：無料で https つき。コードの保管場所と公開場所が同じ。比べた相手：レンタルサーバー、Vercel など
- **TypeScript**：書いている途中で赤ペンを入れてくれる先生。AI が書いたコードの間違いも見つけやすい
- **Vite**：書いたコードをスマホで速く動く形にまとめる組み立て工場
- **React を使わない**：画面が3つほどの小さなアプリには大きすぎる。部品が少ないほど守る場所も少ない
- **JSON に分ける**：台本（文章）と役者（プログラム）を分ける。文章だけ直せる
- **Vitest**：「この答えならライオン・どっしり型になるはず」を自動で確かめる
- **pnpm**：速く、安全の設定（新しすぎる部品をすぐ使わない）が強め

## 12. セキュリティとプライバシー〔ゆ〕〔C〕

作者の希望：**脆弱性はしっかりつぶす**。

| 対策 | 内容 |
|---|---|
| サーバーのプログラムを持たない | 静的サイトなので、PHP などサーバー側の脆弱性の影響を受けない |
| 外部に送らない | 回答・結果は `localStorage` のみ。アクセス解析・広告・外部フォント・外部スクリプトを入れない |
| Vite の版 | **8.0.16 以上**（CVE-2026-53571：Windows で `.env` などが見えてしまう問題の修正版）。ほかの既知の問題（CVE-2026-39365 など）も修正ずみの版 |
| 開発サーバー | 自分のパソコンの中だけで動かす（`--host` でネットワークに出さない） |
| pnpm の設定 | 公開から24時間たっていない部品は入れない（`minimumReleaseAge`）。部品のインストール時スクリプトは許可したものだけ。**設定する前に pnpm の公式の説明で確かめる** |
| 部品の固定 | `pnpm-lock.yaml` をコミットし、CI では `pnpm install --frozen-lockfile` |
| 脆弱性の見張り | GitHub の Dependabot を有効にし、CI で `pnpm audit` を実行する |
| 画面への書き出し | 文章は `textContent` などで入れ、`innerHTML` に文字列を流しこまない |
| CSP | `<meta http-equiv="Content-Security-Policy">` で、自分のサイト以外からの読み込みを禁止する |
| `.gitignore` | `.env*`（`.env.example` は除く）・`*.pem`・`*.key`・`id_rsa`・`id_ed25519`・`credentials.csv`・`*-service-account.json`・`.superpowers/` |
